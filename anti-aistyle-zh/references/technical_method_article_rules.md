# 技术方法文与内部经验分享稿规则

这份文件处理技术方法文、内部工程经验分享、工程复盘、工具使用文章，以及含 prompt 示例、checklist、命令、路径、函数名、日志或测试结果的中文长文。

核心目标：降低成熟经验分享腔、解释填缝和词频残留，同时保住技术事实、可复制 prompt、工程约束和执行边界。

## 快速路由

- 文本是技术方法文 / 内部分享稿 / 工程复盘 / 使用经验文章时读本文件。
- 文本超过 `3000` 字且已经改过一轮，或用户要求“继续优化 / 按词频看一下 / 某个词仍很多”时读本文件。
- 含 fenced code block、prompt 示例、checklist、命令、路径、函数名、日志、测试结果时读本文件。
- 本文件不替代事实保真；原文没有给出的事实、数据、路径、函数、命令结果和工程结论不能新增。

## 1. 体裁识别

命中以下特征时，不按普通评论文或散文处理：

- 文章给工程同学、研发团队、内部读者看。
- 主题是工具使用、调试、排查、研发流程、AI Agent 实践、代码协作或工程复盘。
- 正文包含 prompt 示例、checklist、命令、路径、函数名、日志、测试结果、报告目录、验证方式。
- 目标是“可复用 / 可执行 / 可验收”，不是文学化或公众号化。

默认强度按 `保守` 或 `平衡偏保守` 执行；用户明确要求去味更重时，也不能牺牲硬信息和执行边界。

## 2. 必须保留的硬信息

这些内容即使重复，也不能仅因“像工具文”就自然化、口语化或删掉：

- 文件路径、目录名、函数名、变量名、包名、命令、命令输出。
- prompt 示例、可复制字段、checklist、编号问题、验收条件。
- 工程约束：只读目录、禁止范围、可写范围、生产代码边界、回滚要求。
- 风险分类、验证方法、证据链路、案例中的输入 / 产物 / 验收。
- 主题词：`任务 / 问题 / 证据 / 验证 / 流程 / 报告 / 链路 / 排查 / 风险 / 路径 / 日志 / prompt / checklist / review`。

主题词高频不等于 AI 味；只在它们周围长出解释胶水、总结腔或成熟顾问腔时处理。

## 3. 高频功能词二扫

长文、二改或用户要求词频检查时，内部统计这些高风险功能词：

```text
可以
需要
应该
可能
很
更
其实
这样
直接
最后
说明
总结
建议
把
变成
让它
这类
```

判断规则：

- 如果词承担解释填缝、模板推进、立场缓冲、程度垫词或结论盖章，改。
- 如果词在 prompt 示例、checklist 字段、命令式操作、专业术语或必要约束里，保留或低介入改。
- 不要求固定降到某个数量；看存在感是否比原文和同体裁真人常态更像模板。

优先检查位置：

- 段首、段尾、小标题后第一句。
- prompt 示例前后的解释句。
- 案例收束句、结语、二改后的补丁句。

## 4. 功能分类与改法

解释填缝：

```text
这样问 -> 这么问 / 这个问法会
需要说明 -> 要交代 / 要写清
说明了什么 -> 指向什么 / 列出什么
可以看到 -> 能看到 / 这里露出来的是
```

缓冲判断：

```text
可能是 A，也可能是 B -> 有时是 A，有时是 B
应该写进 DESIGN.md -> 适合写进 DESIGN.md
可以拆成 -> 拆成
```

程度垫词：

```text
很关键 -> 关键
风险很高 -> 风险高
很难复用 -> 难复用
更稳 / 更适合 -> 稳一点 / 更贴这个场景
```

结构过渡：

```text
最后一个案例 -> 收尾案例
最后靠什么验收 -> 最终靠什么验收
接下来需要 -> 接下来
```

模板动词：

```text
把 X 变成 Y -> X 进入 Y / X 沉淀成 Y / 将 X 写回 Y / X 转向 Y
把经验变成文档 -> 经验要进入文档
把线上 DAG 翻译成离线流程 -> 将线上 DAG 翻译成离线流程
```

不要把技术文改成：

```text
这个事吧，其实就是...
说白了...
你就先...
```

这会把工程文章洗成口语散文。

## 5. 点名词强审

用户说类似这些话时触发：

```text
“X”这样的词仍然很多
单字“X”是否也类似
X 的存在感太强
继续压一下 X
统计词频，看哪些与 AI 味相关，直接修正
```

执行顺序：

1. 扫全文中该词全部位置。
2. 按功能分类：模板骨架、约束 / prompt / checklist、专业术语、可自然改掉的视觉重复。
3. 先改模板骨架和视觉重复。
4. 约束、prompt、checklist、术语只做低介入处理。
5. 用户明确继续压时，可进入更强词面优化，但不能改软硬约束。

对 `不是 / 不` 的默认规则：

- 高风险：`不是...而是...`、`不只是...更...`、`不能只...`、`不要只...`、`不等于...`、`不应该只是...`、`不会自动...`、`不是一个...`、`不在...而在...`。
- 可保留：prompt 中的硬约束、checklist 中的边界问题、专业术语、事实判断。
- 用户连续点名时，优先转正向表达，而不是机械删掉含义。

## 6. 正向约束改写

当 `不要 / 不能 / 不应该 / 不属于 / 没有` 承担约束或边界功能时，优先改成正向硬边界：

```text
不要改代码 -> 保持代码原样
不能动哪些目录 -> 哪些目录只读
不能只看文件名 -> 文件名只能提供线索
不要只问原因 -> 少问“原因是什么”，先要证据
不要直接下结论 -> 最后再下结论
不要把无关重构混进来 -> 无关重构留到后续任务
不属于本次改动 -> 应留到后续
没有要求验证 -> 缺少验证要求
没有落成交付物 -> 缺少交付物
```

禁止把硬约束改软：

```text
不要修改生产代码 -> 尽量不要修改生产代码
```

应改成：

```text
生产代码只读
```

## 7. Prompt 示例特殊区

fenced code block、prompt 示例、checklist 和可复制字段不是普通正文。

可改：

- 语义重复的否定句。
- AI 腔明显的长句。
- 不必要的解释。
- 可转成正向约束的表达。

不应改：

- 必要命令式语气。
- 明确边界和编号结构。
- checklist 问句。
- 用户可复制的字段名。
- 生产代码、bak 目录、输出路径、验证命令等硬信息。

例：

```text
请不要只给结论 -> 请先给证据，再给结论
不要继续扩展功能 -> 保持当前功能范围
```

这些结构本身应保留：

```text
哪些目录只读？
哪些目录可写？
哪些输出文件名或路径需要沿用？
```

## 8. 二扫复查

每轮修改后检查：

- 技术含义有没有变。
- 文件路径、函数名、命令、日志、变量名有没有被自然化。
- prompt 是否还能复制使用。
- checklist 是否仍清楚。
- 只读、禁止、验证、验收边界有没有变软。
- 高频功能词是否明显下降，且主题词没有被误伤。
- 正文没有被压成摘要，也没有被改成口语散文。
